PART 0 STM32 이해하기 · 약 55분 · 기초

T02Cortex-M 코어 구조

RISC·하버드·Thumb-2, 코어 레지스터(R0~R15, xPSR), 스레드·핸들러 모드와 특권 레벨, 함수 호출 규약, 예외 진입 스태킹, M0·M3·M4·M7·M33 의 차이와 CMSIS-Core 함수를 익힙니다.

선수 레슨: T01
HAL 레퍼런스

학습 목표#

  • Cortex-M 이 RISC · 하버드 구조 · Thumb-2 명령 집합을 가진 코어라는 것을 각 용어의 뜻과 함께 설명할 수 있습니다.
  • 코어 레지스터 R0~R12, SP(MSP/PSP), LR, PC, xPSR 과 특수 레지스터(PRIMASK · BASEPRI · CONTROL)의 역할을 압니다.
  • 스레드 모드 · 핸들러 모드, 특권 · 비특권 레벨이 무엇이고 언제 바뀌는지 압니다.
  • C 함수 호출이 레지스터와 스택을 어떻게 쓰는지(AAPCS)를 알고, 예외 진입 때 하드웨어가 8워드를 자동으로 스태킹하는 이유를 설명할 수 있습니다.
  • M0 · M0+ · M3 · M4 · M7 · M33 의 차이(FPU · DSP · MPU · 캐시 · TrustZone)를 표로 구분하고, DMIPS 와 CoreMark 수치를 읽을 수 있습니다.
  • CMSIS-Core 의 __disable_irq(), __NOP(), NVIC_* 함수가 어떤 명령·레지스터로 이어지는지 압니다.

코어와 MCU 의 경계#

STM32 칩 안에서 Arm 이 설계한 부분은 코어(CPU) · NVIC · SysTick · 디버그 블록이고, 나머지(GPIO · 타이머 · UART · 플래시 컨트롤러 · 클럭 회로)는 ST 가 설계합니다. 그래서 Cortex-M 에 관한 문서는 Arm 이(PM0214 는 ST 가 Arm 문서를 정리한 것), 주변장치 문서는 ST 가(RM0383) 씁니다.

코어가 같으면 레지스터 · 명령 · 예외 처리 · 스택 규칙은 모든 제조사의 MCU 에서 같습니다. NXP, Nordic, Microchip 의 Cortex-M4 도 이 레슨의 내용이 그대로 적용됩니다.

RISC · 하버드 · Thumb-2#

RISC#

Cortex-M 은 RISC(Reduced Instruction Set Computer) 입니다. 명령 하나가 하는 일이 단순하고(레지스터끼리 연산, 메모리 로드/스토어 분리), 대부분의 명령이 1 사이클에 끝납니다. 메모리에 있는 값을 계산하려면 반드시 레지스터로 읽어 와서(LDR) 계산하고 다시 쓰는(STR) 로드/스토어 구조입니다.

text
GPIOA->ODR ^= (1 << 5);        // C 한 줄은
  ldr  r3, [r2, #20]           // 1. ODR 을 r3 으로 읽고     (r2 = GPIOA 베이스, 0x14 = ODR 오프셋)
  eor  r3, r3, #32             // 2. 비트 5 를 반전하고
  str  r3, [r2, #20]           // 3. 다시 씀  → 읽기·수정·쓰기 (RMW) 세 명령

이 세 명령 사이에 인터럽트가 끼어들 수 있다는 점이 T05 의 BSRR 이야기로 이어집니다.

하버드 구조#

명령 버스(I-bus)와 데이터 버스(D-bus)가 분리되어 있어 명령 페치와 데이터 접근이 동시에 일어납니다. Cortex-M3/M4 는 세 개의 AHB-Lite 버스를 가집니다.

버스주소 범위용도
I-Code0x0000_0000 ~ 0x1FFF_FFFF명령 페치 (플래시)
D-Code0x0000_0000 ~ 0x1FFF_FFFF코드 영역의 데이터 읽기 (상수 테이블, 리터럴 풀)
System0x2000_0000 ~ 0xDFFF_FFFFSRAM, 주변장치, 외부 메모리

주소 공간은 하나(폰 노이만처럼 통합)지만 버스가 나뉘어 있어 "수정된 하버드" 라고 부릅니다. SRAM 에 놓인 코드를 실행하면 System 버스로 명령을 가져오므로 조금 느려질 수 있습니다. Cortex-M0/M0+ 는 버스가 하나(폰 노이만)입니다.

Thumb-2#

Arm 코어는 원래 32비트 고정 길이 명령(A32)을 썼습니다. Thumb 은 자주 쓰는 명령을 16비트로 줄인 것이고, Thumb-2 는 16비트와 32비트 명령을 섞어 쓰는 집합입니다. Cortex-M 은 Thumb-2 만 실행합니다. 그래서 다음 두 가지가 따라옵니다.

  • 코드 밀도가 높습니다. 같은 프로그램이 A32 보다 25~30 % 작습니다 (Arm 발표 수치 기준).
  • 모든 코드 주소의 최하위 비트(bit 0)가 1 이어야 합니다. 이 비트는 "Thumb 상태" 표시(xPSR 의 T 비트로 들어감)이며, 벡터 테이블에 있는 핸들러 주소가 모두 홀수인 이유입니다. 함수 포인터에 짝수 주소를 넣고 호출하면 HardFault 가 납니다.

Cortex-M0/M0+ 는 Thumb-2 의 부분집합(대부분 16비트 명령, 32비트는 BL·MSR·MRS·DMB·DSB·ISB 정도)만 지원합니다. 그래서 M0 용 코드는 M4 에서 돌지만 반대는 안 됩니다.

두 개의 스택 포인터#

SP 는 물리적으로 MSP(Main SP) 와 PSP(Process SP) 두 개입니다.

  • 리셋 직후와 모든 예외 핸들러는 MSP 를 씁니다.
  • 스레드 모드에서 CONTROL.SPSEL = 1 이면 PSP 를 씁니다. RTOS 가 각 태스크에 PSP 를 따로 주고, 커널과 인터럽트는 MSP 를 쓰도록 나눕니다.
  • HAL 만 쓰는 이 강좌의 코드는 처음부터 끝까지 MSP 하나만 씁니다. 링커 스크립트의 _estack (F411: 0x2002_0000 = SRAM 끝) 이 그 초기값입니다.

스레드 모드 (Thread)핸들러 모드 (Handler)
언제main() 을 포함한 보통 코드예외·인터럽트 핸들러 실행 중
특권특권 또는 비특권 (CONTROL.nPRIV)항상 특권

리셋하면 스레드 모드 · 특권으로 시작합니다. HAL 프로젝트는 계속 특권 상태로 돌기 때문에 모든 레지스터에 접근할 수 있고, cpsid i 로 인터럽트를 끌 수도 있습니다. 비특권으로 내려가면(CONTROL.nPRIV = 1) 시스템 레지스터 접근과 cpsid 가 금지되고, MPU 로 막은 영역을 건드리면 MemManage 폴트가 납니다. 비특권에서 특권으로 올라가는 유일한 길은 SVC 명령으로 예외를 일으키는 것이며, RTOS 의 시스템 콜이 이 구조를 씁니다.

HAL_GPIO_EXTI_Callback 처럼 인터럽트에서 불리는 함수 안에서 __get_IPSR() 을 읽으면 0 이 아닌 값이 나옵니다. "지금 ISR 안인가?" 를 판단하는 표준 방법입니다.

함수 호출과 스택 (AAPCS)#

Arm 의 호출 규약 AAPCS(Procedure Call Standard for the Arm Architecture) 는 컴파일러가 지켜야 하는 약속입니다.

  1. 인자는 R0, R1, R2, R3 순서로 넘기고, 5번째부터는 스택에 쌓습니다. 64비트 인자(uint64_t, double)는 짝수 레지스터 쌍(R0:R1, R2:R3)을 씁니다.
  2. 반환값은 R0 (64비트는 R0:R1) 입니다. 구조체가 크면 호출자가 공간을 마련해 주소를 R0 로 넘깁니다.
  3. R0~R3, R12 는 호출된 함수가 마음대로 써도 됩니다 (caller-saved). 값을 지키고 싶으면 호출자가 미리 저장합니다.
  4. R4~R11 은 호출된 함수가 쓰려면 반드시 저장하고 복원해야 합니다 (callee-saved). 함수 첫머리의 push {r4, r5, lr} 가 그것입니다.
  5. 스택은 아래로 자라며(full-descending), 함수 경계에서 8바이트 정렬을 유지합니다.
c
uint32_t add3(uint32_t a, uint32_t b, uint32_t c) { return a + b + c; }
/*   add  r0, r0, r1      ; a + b          — r0 = a, r1 = b, r2 = c 로 들어옴
     add  r0, r0, r2      ; + c            — 결과를 r0 에
     bx   lr              ; 복귀 (lr 에 호출 다음 주소)                                   */

인자가 넷 이하이고 지역 변수가 적으면 함수가 스택을 전혀 쓰지 않을 수 있습니다. bl 명령이 복귀 주소를 LR 에 넣고, 다른 함수를 또 부르려면 그 LR 을 스택에 push 해야 합니다.

왜 하드웨어가 딱 8워드를 스태킹하는가

AAPCS 에 따르면 어떤 C 함수를 부르든 R0~R3, R12, LR 은 깨질 수 있고 R4~R11 은 그 함수가 알아서 지킵니다. 그래서 예외가 났을 때 코어는 caller-saved 인 R0~R3 · R12 · LR 과, 복귀에 필요한 PC · xPSR — 합쳐서 8워드 — 만 스택에 넣어 두면 핸들러를 보통의 C 함수로 쓸 수 있습니다. 핸들러가 R4~R11 을 쓰면 컴파일러가 스스로 push/pop 하기 때문입니다. 이 설계 덕분에 Cortex-M 은 어셈블리 래퍼 없이 void EXTI0_IRQHandler(void) 를 그대로 벡터 테이블에 넣을 수 있습니다.

파이프라인과 실행 시간#

Cortex-M3/M4 는 3단 파이프라인(페치 → 디코드 → 실행) 입니다. 명령 대부분이 1 사이클이지만 다음은 예외입니다.

명령사이클 (M3/M4)비고
산술 · 논리 · 시프트1
32 × 32 곱셈 mul1M0 은 1 또는 32 (구현 선택)
나눗셈 udiv sdiv2 ~ 12값에 따라 다름. M0/M0+ 는 하드웨어 나눗셈 없음 (라이브러리 호출, 수십 사이클)
로드 ldr2 (연속이면 파이프라이닝)플래시 대기 상태가 더해질 수 있음
분기 (taken)2 ~ 4파이프라인 비움. M3/M4 는 분기 예측 없음, M7 은 있음
bl 함수 호출2 ~ 4

플래시가 코어보다 느리기 때문에(F411 84 MHz 에서 2 대기 상태, T04) ST 는 F4 에 ART Accelerator(명령 프리페치 + 64 × 128비트 캐시)를 넣어 0 대기 상태처럼 보이게 합니다. Cortex-M7 은 6단 슈퍼스칼라(1 사이클에 2 명령) 파이프라인과 진짜 L1 캐시(명령·데이터)를 가집니다. M0+ 는 2단 파이프라인이라 분기 손실이 작습니다.

HAL_Delay(1) 이 84 MHz 에서 84,000 사이클이라는 것, for 루프 한 바퀴가 대략 3~5 사이클이라는 것을 감으로 알아 두면 "이 코드가 1 ms 안에 끝나는가" 를 어림할 수 있습니다.

예외 진입과 복귀#

예외(exception)는 인터럽트를 포함하는 넓은 말입니다. Cortex-M 에서는 리셋 · NMI · HardFault · SVC · PendSV · SysTick 같은 시스템 예외 1~15번과 주변장치 인터럽트(IRQ) 16번부터가 하나의 벡터 테이블에 놓입니다.

진입 과정은 그림의 1~5 단계입니다. 핵심은 하드웨어가 스태킹 · 벡터 페치 · 복귀를 모두 처리하므로 핸들러가 보통의 C 함수라는 것입니다. 진입 지연은 M3/M4 에서 12 사이클(0 대기 상태 메모리 기준), M0 16, M0+ 15, M7 12 사이클입니다. 84 MHz 에서 12 사이클은 약 143 ns 입니다.

복귀는 핸들러가 bx lr 를 실행할 때 LR 에 든 EXC_RETURN 값을 보고 일어납니다.

EXC_RETURN뜻
0xFFFF_FFF1핸들러 모드로 복귀, MSP (중첩 인터럽트에서 복귀)
0xFFFF_FFF9스레드 모드로 복귀, MSP (HAL 프로젝트의 보통 경우)
0xFFFF_FFFD스레드 모드로 복귀, PSP (RTOS 태스크로 복귀)
0xFFFF_FFE1 / E9 / ED위와 같되 FPU 문맥이 스택에 있음 (M4F, M7)

디버거에서 폴트가 나 멈췄을 때 LR 이 0xFFFFFFF9 이면 "메인 코드 실행 중 예외 진입" 이라는 뜻이고, 스택의 여섯 번째 워드(PC)를 보면 폴트가 난 명령 주소를 알 수 있습니다.

예외 중첩과 우선순위

높은 우선순위(숫자가 작은) 예외는 실행 중인 낮은 우선순위 핸들러를 다시 8워드 스태킹하고 끼어듭니다. 이때 LR = 0xFFFF_FFF1 입니다. 한 핸들러가 끝날 때 대기 중인 다른 예외가 있으면 pop → push 를 생략하고 바로 다음 핸들러로 가는 테일체이닝(tail-chaining, 6 사이클) 이 일어납니다. T06 에서 NVIC 우선순위와 함께 다룹니다.

DMIPS 와 CoreMark#

  • DMIPS(Dhrystone MIPS)는 1980년대 벤치마크 Dhrystone 기준의 정수 성능입니다. 컴파일러 최적화에 민감하고 실제 코드와 다르지만, 제조사가 오래 써 온 지표입니다. F411 은 DS10314 에서 125 DMIPS (1.25 DMIPS/MHz × 100 MHz), H743 은 480 MHz 에서 1027 DMIPS 로 표기됩니다.
  • CoreMark 는 EEMBC 가 만든 더 현대적인 지표로 리스트 처리 · 행렬 · 상태 기계 · CRC 를 섞어 잽니다. 코어 등급 비교에는 CoreMark/MHz 가 더 공정합니다.
  • 두 값 모두 코어 만의 수치입니다. 실제 성능은 플래시 대기 상태, 캐시, 버스 경합에 따라 달라지므로 "84 MHz F411 이 72 MHz F103 보다 1.17배 빠르다" 처럼 단순 비교하면 안 됩니다.

리셋 직후에 일어나는 일#

  1. 코어가 주소 0x0000_0000 에서 초기 MSP 값을, 0x0000_0004 에서 Reset_Handler 주소를 읽습니다. 이 주소에는 BOOT 핀 설정에 따라 플래시(0x0800_0000)가 비쳐 있습니다 (T03).
  2. Reset_Handler(startup_stm32f411xetx.s)가 SystemInit() 을 불러 FPU 접근을 켜고(CPACR), VTOR 를 설정합니다.
  3. 플래시에 있는 .data 초기값을 SRAM 으로 복사하고, .bss 를 0 으로 채웁니다.
  4. __libc_init_array() 로 C++ 생성자 · 라이브러리 초기화를 하고 main() 을 부릅니다.
  5. main() 이 HAL_Init() 을 부르면 NVIC 그룹, SysTick 1 ms, 플래시 프리페치 · 캐시가 설정되고, SystemClock_Config() 가 PLL 을 켭니다 (T04).

이 순서를 알면 "전역 변수 초기값이 왜 자동으로 들어가는가", "main() 전에 클럭이 왜 16 MHz 인가" 같은 질문에 답할 수 있습니다.

과제#

  1. uint32_t f(uint32_t a, uint32_t b, uint32_t c, uint32_t d, uint32_t e) 를 호출할 때 각 인자가 어디에 놓이는지, 반환값은 어디에 오는지 적으세요.
  2. 예외 진입 때 스택에 쌓이는 8워드를 낮은 주소부터 순서대로 쓰고, 왜 R4~R11 은 쌓지 않는지 AAPCS 로 설명하세요.
  3. CubeIDE 프로젝트의 startup_stm32f411xetx.s 를 열어 Reset_Handler 가 하는 일을 순서대로 적고, .data 복사 루프를 찾으세요.
  4. F411 (M4F, 100 MHz) 과 F103 (M3, 72 MHz) 의 DMIPS 를 계산하고, float 를 많이 쓰는 코드에서 두 칩의 실제 성능 차이가 DMIPS 비율보다 큰 이유를 쓰세요.
  5. (실물) 디버거로 HAL_GPIO_EXTI_Callback 안에 중단점을 걸고 레지스터 창의 LR · xPSR(IPSR) · SP 값을 기록한 뒤, 이 레슨의 표와 대조하세요.
