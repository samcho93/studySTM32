T06인터럽트·예외와 NVIC

벡터 테이블과 IRQHandler 이름 규칙, NVIC 우선순위(프리엠션·서브·그룹), 테일체이닝, EXTI 라인 매핑과 SYSCFG, HAL 인터럽트 흐름, ISR 작성 규칙, SysTick 우선순위 함정, 폴링·인터럽트·DMA 비교를 익힙니다.

선수 레슨: T02
시뮬레이터에서 실습

학습 목표#

  • 벡터 테이블이 startup_stm32f411xetx.s 에 어떻게 놓여 있고, xxx_IRQHandler 이름 규칙이 어떻게 링크되는지 설명할 수 있습니다.
  • NVIC 우선순위의 4비트 · 프리엠션/서브 · 우선순위 그룹을 이해하고 HAL_NVIC_SetPriority 의 두 숫자를 올바르게 정할 수 있습니다.
  • 테일체이닝 · late arrival 이 무엇인지, EXTI 라인이 핀 번호와 SYSCFG_EXTICR 로 어떻게 매핑되는지, pending 플래그를 왜 지워야 하는지 압니다.
  • IRQHandler → HAL_xxx_IRQHandler → Callback 으로 이어지는 HAL 인터럽트 흐름을 따라갈 수 있습니다.
  • ISR 작성 규칙(짧게, volatile, 공유 데이터 보호, HAL_Delay 금지)과 SysTick 우선순위 함정, 폴링 · 인터럽트 · DMA 의 선택 기준을 압니다.

벡터 테이블#

벡터 테이블은 "예외 번호 × 4" 오프셋에 핸들러 주소를 늘어놓은 배열입니다. CubeMX 가 만든 startup_stm32f411xetx.s 에 어셈블리로 들어 있습니다.

textstartup_stm32f411xetx.s (일부)
  .section .isr_vector,"a",%progbits
g_pfnVectors:
  .word  _estack                 /* 0x00  초기 MSP (링커 스크립트) */
  .word  Reset_Handler           /* 0x04 */
  .word  NMI_Handler             /* 0x08 */
  .word  HardFault_Handler       /* 0x0C */
  ...
  .word  SysTick_Handler         /* 0x3C */
  .word  WWDG_IRQHandler         /* 0x40  IRQ 0 */
  .word  PVD_IRQHandler          /* 0x44  IRQ 1 */
  ...
  .word  EXTI0_IRQHandler        /* 0x58  IRQ 6 */
  ...
  .word  EXTI9_5_IRQHandler      /* 0x9C  IRQ 23 */
  .word  TIM3_IRQHandler         /* 0xB4  IRQ 29 */
  ...
  .word  USART2_IRQHandler       /* 0xD8  IRQ 38 */
  .word  EXTI15_10_IRQHandler    /* 0xE0  IRQ 40 */
  ...
  .weak      EXTI15_10_IRQHandler
  .thumb_set EXTI15_10_IRQHandler,Default_Handler     /* 정의하지 않으면 Default_Handler (무한 루프) */
  • 모든 핸들러는 weak 심볼로 Default_Handler(무한 루프)에 묶여 있습니다. 사용자가 같은 이름의 C 함수를 정의하면 링커가 그것으로 바꿔 줍니다. 그래서 stm32f4xx_it.c 에 void EXTI15_10_IRQHandler(void) 를 쓰기만 하면 벡터 테이블에 들어갑니다.
  • 이름을 한 글자라도 틀리면 컴파일 오류 없이 조용히 Default_Handler 가 남아, 인터럽트가 나는 순간 프로그램이 무한 루프에 갇힙니다. "인터럽트 켜면 멈춘다" 의 가장 흔한 원인입니다.
  • IRQn_Type 열거형(stm32f411xe.h)이 이름과 번호를 잇습니다: EXTI15_10_IRQn = 40, TIM3_IRQn = 29, USART2_IRQn = 38, 시스템 예외는 음수 (SysTick_IRQn = -1, PendSV_IRQn = -2, SVCall_IRQn = -5).
  • F411 은 벡터 위치 85 (SPI5) 까지 있고 그중 일부는 예약(비어 있음)입니다. F103 은 위치 59 까지 (RM0008), 이름도 조금 다릅니다 (USB_LP_CAN1_RX0_IRQn 등).

NVIC 우선순위#

NVIC(Nested Vectored Interrupt Controller) 는 코어 안에 있으며, 각 IRQ 의 인에이블 · pending · 우선순위를 관리하고 가장 급한 것을 코어에 넘깁니다.

SCB->AIRCR.PRIGROUP프리엠션/서브 비트 나누기NVIC_SetPriorityGrouping

4비트, 16 단계#

STM32 는 우선순위 8비트 중 상위 4비트만 구현하므로 0 ~ 15 의 16 단계이고, 숫자가 작을수록 급합니다. 0 이 가장 높고 15 가 가장 낮습니다. 이 4비트를 프리엠션(preemption) 우선순위와 서브(sub) 우선순위로 나누는 것이 우선순위 그룹입니다.

그룹프리엠션 비트서브 비트프리엠션 단계서브 단계
NVIC_PRIORITYGROUP_004116
NVIC_PRIORITYGROUP_11328
NVIC_PRIORITYGROUP_22244
NVIC_PRIORITYGROUP_33182
**NVIC_PRIORITYGROUP_4**40161
  • 프리엠션 우선순위가 더 높은(숫자가 작은) 인터럽트만 실행 중인 핸들러를 끼어들 수 있습니다 (중첩).
  • 서브 우선순위는 프리엠션이 같은 인터럽트 둘이 동시에 대기 중일 때 어느 것을 먼저 할지만 정합니다. 끼어들지는 못합니다.
  • 둘 다 같으면 IRQ 번호가 작은 것이 먼저입니다.
  • HAL_Init() 이 그룹 4 로 설정하므로 HAL 프로젝트에서 서브 우선순위는 언제나 0 이고, HAL_NVIC_SetPriority(IRQn, pre, sub) 의 sub 는 무시됩니다. CubeMX 의 NVIC 탭에서 보이는 두 열이 이것입니다.
c
HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4);      /* HAL_Init 이 이미 함 */
HAL_NVIC_SetPriority(EXTI15_10_IRQn, 5, 0);              /* 버튼: 중간 */
HAL_NVIC_EnableIRQ(EXTI15_10_IRQn);
HAL_NVIC_SetPriority(TIM3_IRQn, 2, 0);                   /* 제어 주기 타이머: 더 급함 → 버튼 ISR 을 끼어들 수 있음 */
HAL_NVIC_EnableIRQ(TIM3_IRQn);
HAL_NVIC_SetPriority(USART2_IRQn, 6, 0);                 /* 수신: 버튼보다 낮음 */
HAL_NVIC_EnableIRQ(USART2_IRQn);

HAL_NVIC_SetPriority 는 NVIC_EncodePriority(그룹, pre, sub) 로 4비트 값을 만든 뒤 NVIC_SetPriority 를 부릅니다. 그룹 4 에서는 그냥 pre 가 그대로 4비트 값이 됩니다.

우선순위를 정하지 않으면

CubeMX 기본값은 모든 인터럽트가 프리엠션 0 입니다. 그러면 모두 같은 급이라 서로 끼어들지 못하고, 실행 중인 핸들러가 끝날 때까지 다른 것은 기다립니다. 간단한 프로그램은 이대로도 동작하지만, 긴 ISR(UART 로 여러 바이트 보내기 등)이 있으면 타이머 인터럽트가 밀립니다. 급한 것에 작은 숫자를 주는 습관을 들이세요. FreeRTOS 를 쓰면 configMAX_SYSCALL_INTERRUPT_PRIORITY(보통 5) 보다 급한 인터럽트에서는 RTOS API 를 부를 수 없다는 규칙이 추가됩니다.

테일체이닝과 late arrival#

  • 테일체이닝(tail-chaining): 핸들러 A 가 끝났는데 B 가 대기 중이면, A 의 8워드 pop 과 B 의 push 를 생략하고 곧바로 B 로 갑니다. 6 사이클이면 됩니다. 연속된 인터럽트를 효율적으로 처리하는 하드웨어 최적화이며 소프트웨어가 신경 쓸 것은 없습니다.
  • late arrival: A 로 진입하기 위해 스태킹하는 도중 더 급한 B 가 오면, 스태킹은 그대로 쓰고 벡터만 B 로 바꿔 B 를 먼저 실행한 뒤 A 를 테일체이닝합니다.
  • pop preemption: A 의 복귀(언스태킹) 중에 새 인터럽트가 오면 언스태킹을 버리고 바로 진입합니다.

이 세 가지 덕분에 Cortex-M 은 인터럽트 사이의 오버헤드가 작고 예측 가능합니다. 12 사이클 진입 · 12 사이클 복귀 · 6 사이클 테일체인이라는 숫자를 기억해 두세요.

EXTI: 핀 → 인터럽트#

GPIO 핀은 NVIC 에 직접 연결되지 않고 EXTI(External Interrupt/event controller) 를 거칩니다.

EXTI 라인연결IRQ (F411)
0 ~ 15GPIO 핀 번호 (PA0 · PB0 · … 중 SYSCFG_EXTICR 로 하나 선택)EXTI0 ~ EXTI4 는 각각, 5~9 는 EXTI9_5 (IRQ 23) 로 공유, 10~15 는 EXTI15_10 (IRQ 40) 로 공유
16PVD (전압 감시)PVD_IRQn
17RTC 알람RTC_Alarm_IRQn
18USB OTG FS 웨이크업OTG_FS_WKUP_IRQn
21RTC 탬퍼 · 타임스탬프TAMP_STAMP_IRQn
22RTC 웨이크업RTC_WKUP_IRQn

핵심 규칙 두 가지입니다.

  1. 핀 번호 = EXTI 라인 번호. PC13 은 라인 13, PA0 은 라인 0 입니다.
  2. 같은 번호의 핀은 한 번에 하나만. PA5 와 PB5 는 둘 다 라인 5 이므로 동시에 EXTI 로 쓸 수 없습니다. 어느 포트를 라인에 붙일지 SYSCFG->EXTICR[n] (4비트 필드, 0 = PA, 1 = PB, 2 = PC …) 이 정합니다. F1 은 AFIO->EXTICR 입니다.
c
/* HAL_GPIO_Init 이 PC13 을 GPIO_MODE_IT_FALLING 으로 설정할 때 하는 일 (요약) */
__HAL_RCC_SYSCFG_CLK_ENABLE();
SYSCFG->EXTICR[3] = (SYSCFG->EXTICR[3] & ~(0xF << 4)) | (2 << 4);   /* 라인 13 ← 포트 C (EXTICR4, 필드 1) */
EXTI->FTSR |=  (1 << 13);     /* 하강 에지 감지 */
EXTI->RTSR &= ~(1 << 13);     /* 상승 에지 끔 */
EXTI->IMR  |=  (1 << 13);     /* 인터럽트 마스크 해제 */
/* 그 다음 사용자가 (또는 CubeMX 가) NVIC 를 켬 */
HAL_NVIC_SetPriority(EXTI15_10_IRQn, 0, 0);
HAL_NVIC_EnableIRQ(EXTI15_10_IRQn);

pending 과 clear#

에지가 감지되면 EXTI->PR 의 해당 비트가 1 이 되고(pending), IMR 이 열려 있으면 NVIC 에 요청이 갑니다. PR 비트는 소프트웨어가 1 을 써서 지워야 합니다. 지우지 않으면 핸들러를 나가자마자 요청이 살아 있으므로 같은 핸들러가 다시 불려 무한히 반복됩니다. HAL_GPIO_EXTI_IRQHandler() 가 이 일을 하므로 HAL 사용자는 보통 잊어도 되지만, 레지스터로 직접 쓸 때는 첫 줄이 EXTI->PR = (1 << 13); 이어야 합니다 (|= 가 아니라 = 인 이유: 다른 비트에 1 을 쓰면 그것도 지워집니다).

NVIC 쪽 pending (ISPR) 은 핸들러 진입 때 하드웨어가 지웁니다. 그러나 주변장치 쪽 플래그(EXTI->PR, TIMx->SR 의 UIF, USART->SR 의 RXNE 등)는 주변장치마다 지우는 방법이 다르므로 레퍼런스 매뉴얼을 봐야 합니다. UIF 는 0 을 쓰고, RXNE 는 DR 을 읽으면 지워집니다.

HAL 인터럽트 흐름#

HAL 프로젝트에서 인터럽트는 세 층을 지납니다. 사용자는 맨 아래 콜백만 씁니다.

c
/* 1) stm32f4xx_it.c — CubeMX 생성. 벡터 테이블이 가리키는 진짜 핸들러 */
void EXTI15_10_IRQHandler(void)
{
  HAL_GPIO_EXTI_IRQHandler(GPIO_PIN_13);          /* 어느 핀인지 알려 줌 */
}

/* 2) stm32f4xx_hal_gpio.c — HAL 라이브러리. 플래그 확인 · 클리어 후 콜백 */
void HAL_GPIO_EXTI_IRQHandler(uint16_t GPIO_Pin)
{
  if (__HAL_GPIO_EXTI_GET_IT(GPIO_Pin) != RESET) {   /* EXTI->PR 비트 확인 */
    __HAL_GPIO_EXTI_CLEAR_IT(GPIO_Pin);              /* EXTI->PR = GPIO_Pin  (1 써서 클리어) */
    HAL_GPIO_EXTI_Callback(GPIO_Pin);
  }
}

/* 3) main.c — 사용자. weak 함수를 덮어씀 */
void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
  if (GPIO_Pin == GPIO_PIN_13) { button_flag = 1; }
}

시뮬레이터에서 열기EXTI 로 LED 토글 예제 열기새 창l05-exti

시뮬레이터의 콘솔 탭에는 EXTI 가 발생하고 콜백이 불리는 로그가 남습니다. 버튼을 누르는 순간 메인 루프의 HAL_Delay 가 끝나기 전에 콜백이 먼저 실행되는 것을 확인해 보세요.

짧게. 플래그만 세우고 처리는 메인 루프에서긴 ISR 은 같은 급 · 낮은 급의 인터럽트를 막고 시간 정확도를 무너뜨림. 기준: 수십 µs 이내

volatile uint32_t rx_count;            /* ISR 이 쓰고 메인이 읽음 */
volatile uint8_t  cmd_ready;

void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)   /* ISR 문맥 */
{
  rx_buf[rx_idx++] = rx_byte;
  if (rx_byte == '\n') { cmd_ready = 1; rx_idx = 0; }    /* 플래그만 */
  HAL_UART_Receive_IT(huart, &rx_byte, 1);               /* 다음 바이트 예약 */
}

int main(void) {
  ...
  while (1) {
    if (cmd_ready) {                                     /* 메인에서 처리 */
      cmd_ready = 0;
      handle_command(rx_buf);                            /* printf, 긴 처리 모두 여기서 */
    }
  }
}

우선순위 역전#

우선순위가 낮은 ISR 이 긴 작업을 하는 동안, 그보다 급한 인터럽트가 같은 프리엠션 우선순위이면 끼어들지 못하고 기다립니다. 결과적으로 급한 일이 늦어지는 것이 우선순위 역전입니다. RTOS 에서는 뮤텍스를 쥔 낮은 태스크 때문에 높은 태스크가 막히는 형태로 나타나며, 베어메탈에서는 "모든 인터럽트가 0" 인 CubeMX 기본 설정이 원인일 때가 많습니다.

SysTick 우선순위 함정#

HAL_Delay() 는 uwTick 이 늘어나기를 기다리고, uwTick 은 SysTick_Handler 가 늘립니다. SysTick 의 우선순위가 지금 실행 중인 핸들러보다 급하지 않으면 SysTick 이 실행되지 못하므로 HAL_Delay 는 영원히 끝나지 않습니다.

  • CubeMX 기본에서 SysTick 과 EXTI 가 모두 0 이면 EXTI 콜백 안의 HAL_Delay(50) (디바운스 목적으로 흔히 시도) 은 멈춥니다.
  • SysTick 을 0, EXTI 를 1 이상으로 두면 동작은 하지만 여전히 ISR 안에서 50 ms 를 낭비하는 나쁜 설계입니다. 디바운스는 HAL_GetTick() 시각 비교로 하세요 (L05).
  • HAL 문서는 SysTick 을 가장 높은 우선순위로 두라고 권합니다. FreeRTOS 는 반대로 SysTick 을 가장 낮은 15 로 쓰고 커널 틱으로 삼습니다. 이 경우 HAL_Delay 대신 osDelay 를 씁니다.
  • I2C · UART 의 폴링 HAL 함수(HAL_I2C_Master_Transmit(..., timeout))도 타임아웃 계산에 HAL_GetTick() 을 쓰므로 같은 함정에 걸립니다.

TICK_INT_PRIORITY 는 stm32f4xx_hal_conf.h 에 있고 CubeMX 의 NVIC 탭 "Time base: System tick timer" 항목으로 바꿉니다.

폴링 vs 인터럽트 vs DMA#

폴링인터럽트DMA
방식루프에서 플래그 · 핀을 계속 읽음이벤트가 나면 코어가 핸들러로 점프하드웨어가 메모리 ↔ 주변장치를 직접 복사, 끝나면 인터럽트
반응 시간루프 한 바퀴 (수 µs ~ 수 ms, 불규칙)약 12 사이클 + 우선순위 대기 (수백 ns)즉시 (코어 개입 없음)
CPU 부담계속 소모 (기다리는 동안 다른 일 어려움)이벤트 때만거의 없음
복잡도가장 단순공유 데이터 · 우선순위 관리 필요설정 복잡, 버퍼 관리, 캐시(M7)
알맞은 곳초기화, 간단한 순차 작업, 드문 이벤트버튼, 수신 바이트, 주기 작업, 캡처대량 · 연속 데이터: ADC 스캔, UART 대량 송수신, SPI 디스플레이, 오디오
HAL 함수HAL_UART_ReceiveHAL_UART_Receive_IT + 콜백HAL_UART_Receive_DMA + 콜백

이 강좌의 진행이 이 순서입니다. L04 폴링 → L05 EXTI 인터럽트 → L06 UART 수신 인터럽트 → L09 ADC DMA. 경험칙은 "초당 수천 번 이하의 이벤트는 인터럽트, 그 이상이거나 바이트가 연속으로 오면 DMA" 입니다.

  1. F411 에서 EXTI0 · EXTI4 · EXTI9_5 · EXTI15_10 · TIM2 · USART1 의 IRQ 번호와 벡터 테이블 오프셋을 stm32f411xe.h 또는 RM0383 의 벡터 표에서 찾아 적으세요.
  2. 모터 제어 주기 타이머(TIM3, 1 kHz), 버튼 EXTI, UART 수신, SysTick 네 인터럽트의 우선순위를 정하고 이유를 쓰세요. 그룹 4 기준입니다.
  3. 시뮬레이터의 L05 예제에서 콜백 안에 HAL_Delay(200) 을 넣어 보고 무슨 일이 생기는지 관찰하세요 (시뮬레이터는 실물과 다를 수 있으니, 실물에서는 어떻게 될지 우선순위 표로 예측하세요).
  4. EXTI->PR 을 |= 로 지우는 코드가 왜 다른 라인의 인터럽트를 잃게 하는지 비트 수준에서 설명하세요.
  5. L06 의 명령어 예제에서 ISR 이 하는 일과 메인 루프가 하는 일을 나누어 적고, ISR 작성 규칙 표의 어느 항목을 지키고 있는지 표시하세요.
