L22FreeRTOS 기초

RTOS 가 필요한 이유, 태스크·스케줄러·우선순위·상태, CubeMX FREERTOS(CMSIS_V2) 설정과 생성 코드, osDelay 와 HAL_Delay 의 차이, 스택 크기를 익힙니다.

선수 레슨: L07 L18
시뮬레이터에서 실습HAL 레퍼런스

학습 목표#

  • 슈퍼 루프(while(1))의 한계와 RTOS 가 필요한 이유를 설명합니다.
  • 태스크 · 스케줄러 · 우선순위 · 태스크 상태(Running · Ready · Blocked · Suspended)를 이해합니다.
  • CubeMX 의 FREERTOS(CMSIS_V2) 설정으로 태스크를 만들고, 생성된 코드의 흐름을 읽습니다.
  • osDelay 와 HAL_Delay 의 차이, osDelayUntil 로 주기 작업 만들기를 익힙니다.
  • 스택 크기와 HAL 타임베이스(TIM6) 설정의 의미를 압니다.

왜 RTOS 인가#

지금까지는 while(1) 안에서 여러 일을 차례로 처리했습니다(슈퍼 루프). 일이 늘어나면 문제가 생깁니다.

  • 한 작업이 HAL_Delay(500) 이나 긴 while 로 기다리면 다른 모든 작업이 멈춥니다.
  • HAL_GetTick() 비교로 기다리지 않게 만들 수 있지만(L06 · L07), 작업마다 상태 변수와 시각 변수가 늘어 코드가 복잡해집니다.
  • "버튼 반응은 5 ms 안에, 화면 갱신은 늦어도 됨" 같은 중요도 차이를 표현하기 어렵습니다.

RTOS(Real-Time Operating System)는 작업마다 자기만의 무한 루프를 가진 태스크로 나누고, 스케줄러가 CPU 를 나눠 줍니다. 각 태스크는 마음 놓고 기다려도(osDelay) 됩니다. 기다리는 동안 CPU 는 다른 태스크에게 갑니다.

c
/* 슈퍼 루프 */                          /* RTOS: 태스크 두 개 */
while (1) {                              void BlinkTask(void *arg) { for(;;) { toggle(); osDelay(250); } }
  if (now - t1 >= 250) { ... }           void ReportTask(void *arg) { for(;;) { print(); osDelay(1000); } }
  if (now - t2 >= 1000) { ... }
}

FreeRTOS 는 가장 널리 쓰이는 무료 RTOS 이고, ST 는 그 위에 CMSIS-RTOS2 라는 표준 API(os… 함수)를 얹어 CubeMX 로 제공합니다.

태스크와 스케줄러#

태스크 상태#

text
            osThreadNew
                │
                ▼
   ┌──────► Ready ─────── 스케줄러가 선택 ───► Running
   │          ▲                                  │
   │          │ 시간이 됨 / 신호가 옴             │ osDelay, 큐·세마포어 대기
   │          └────────── Blocked ◄──────────────┘
   │
   └─ osThreadResume ── Suspended ◄── osThreadSuspend
  • Running: 지금 CPU 를 쓰는 태스크 (코어가 하나이므로 한 번에 하나)
  • Ready: 실행할 준비가 되었지만 더 높은(또는 같은) 우선순위 태스크가 CPU 를 쓰는 중
  • Blocked: osDelay, 큐 · 세마포어 대기 등으로 CPU 를 쓰지 않고 기다리는 중
  • Suspended: 명시적으로 멈춤. 다시 깨우기 전까지 선택되지 않음

스케줄링 규칙 (FreeRTOS 기본 설정)#

  1. Ready 중 우선순위가 가장 높은 태스크가 실행됩니다. 더 높은 태스크가 Ready 가 되는 순간 즉시 CPU 를 빼앗습니다(선점).
  2. 우선순위가 같으면 틱(1 ms)마다 번갈아 실행합니다(타임 슬라이싱, 라운드 로빈).
  3. 모두 Blocked 이면 가장 낮은 Idle 태스크가 돕니다. (저전력 설계에서는 Idle 에서 잠들 수 있음)

CMSIS-RTOS2 우선순위 값: osPriorityIdle(1) < osPriorityLow(8) < osPriorityBelowNormal(16) < **osPriorityNormal(24)** < osPriorityAboveNormal(32) < osPriorityHigh(40) < osPriorityRealtime(48).

높은 태스크는 반드시 쉬어야 합니다

높은 우선순위 태스크가 osDelay 나 대기 없이 계속 돌면 그보다 낮은 태스크는 영원히 실행되지 않습니다(굶주림, starvation). 우선순위가 높을수록 "짧게 일하고 곧바로 Blocked" 가 되도록 만듭니다.

CubeMX 에서 FreeRTOS 켜기#

  1. Middleware and Software Packs → FREERTOS → Interface: CMSIS_V2
  2. Tasks and Queues 탭: 기본 defaultTask 가 있습니다. Add 로 태스크를 추가합니다.
    • Task Name blinkTask, Priority osPriorityLow, Stack Size (Words) 128, Entry Function StartBlinkTask, Code Generation Option Default
  3. System Core → SYS → Timebase Source: TIM6 (또는 쓰지 않는 다른 기본 타이머)
  4. Config parameters 의 TOTAL_HEAP_SIZE(기본 15360 바이트)가 모든 태스크 스택 + 큐 등을 담을 만큼인지 확인
왜 Timebase 를 TIM6 으로 바꾸나

FreeRTOS 는 스케줄러 틱으로 SysTick 을 씁니다. HAL 도 기본으로 SysTick 을 HAL_Delay · HAL_GetTick 에 쓰므로, CubeMX 는 HAL 타임베이스를 다른 타이머로 옮기라고 경고합니다. TIM6 으로 바꾸면 main.c 에 HAL_TIM_PeriodElapsedCallback 이 생기고 그 안에서 if (htim->Instance == TIM6) HAL_IncTick(); 을 부릅니다. 시뮬레이터는 이 부분을 생략하고 틱을 내부에서 처리합니다. 실물에서 같은 콜백에 여러분의 타이머 코드를 넣을 때는 USER CODE 구역에 넣어야 지워지지 않습니다.

생성 코드 읽기#

c
/* 핸들과 속성 — CubeMX 가 태스크마다 만듦 */
osThreadId_t blinkTaskHandle;
const osThreadAttr_t blinkTask_attributes = {
  .name = "blinkTask",
  .stack_size = 128 * 4,                       /* 워드 → 바이트 */
  .priority = (osPriority_t) osPriorityLow,
};

int main(void)
{
  HAL_Init(); SystemClock_Config(); MX_GPIO_Init(); MX_USART2_UART_Init();
  /* USER CODE BEGIN 2 */ ... /* USER CODE END 2 */
  osKernelInitialize();                        /* 1) 커널 준비 */
  /* USER CODE BEGIN RTOS_MUTEX / SEMAPHORES / TIMERS / QUEUES */
  defaultTaskHandle = osThreadNew(StartDefaultTask, NULL, &defaultTask_attributes);   /* 2) 태스크 생성 */
  blinkTaskHandle   = osThreadNew(StartBlinkTask,   NULL, &blinkTask_attributes);
  osKernelStart();                             /* 3) 스케줄러 시작 — 여기서 돌아오지 않음 */
  while (1) { }                                /* 도달하지 않음 */
}
  • osKernelStart() 뒤의 while (1) 은 실행되지 않습니다. 코드는 태스크 함수 안에 씁니다.
  • defaultTask 의 본문은 USER CODE BEGIN 5 구역, 추가한 태스크는 USER CODE BEGIN StartBlinkTask 처럼 함수 이름 구역에 씁니다.
  • 태스크 함수는 절대 return 하면 안 됩니다. for(;;) 로 끝나지 않게 하거나, 끝낼 때는 osThreadExit() 을 부릅니다.

예제 1 — 태스크 두 개#

시뮬레이터에서 열기태스크 두 개 열기새 창l22-rtos-blink

USER CODE BEGIN 5 (defaultTask, 보통 우선순위)와 USER CODE BEGIN StartBlinkTask (blinkTask, 낮은 우선순위)에 들어간 코드입니다.

cCore/Src/main.c
void StartDefaultTask(void *argument)
{
  /* USER CODE BEGIN 5 */
  /* Infinite loop */
  for(;;)
  {
    printf("[%5lu] %s: blink_count=%lu\r\n", osKernelGetTickCount(), osThreadGetName(osThreadGetId()), blink_count);
    osDelay(1000);                      // 1000 틱(1 s) 동안 Blocked — 그동안 다른 태스크가 CPU 사용
  }
  /* USER CODE END 5 */
}

void StartBlinkTask(void *argument)
{
  /* USER CODE BEGIN StartBlinkTask */
  /* Infinite loop */
  for(;;)
  {
    HAL_GPIO_TogglePin(LD2_GPIO_Port, LD2_Pin);
    blink_count++;
    osDelay(250);
  }
  /* USER CODE END StartBlinkTask */
}
cCore/Src/main.c
/* USER CODE BEGIN PV */
volatile uint32_t blink_count = 0;      // 두 태스크가 함께 보는 변수
/* USER CODE END PV */

  /* USER CODE BEGIN 2 */
  printf("FreeRTOS start\r\n");
  /* USER CODE END 2 */
text
[    1] defaultTask: blink_count=0
[ 1004] defaultTask: blink_count=5
[ 2007] defaultTask: blink_count=9
  • 두 태스크는 서로를 모릅니다. 각자 자기 주기로 돌고, 공유 변수 blink_count 로만 연결됩니다.
  • 출력 시각이 1004, 2007, 3010 … 으로 조금씩 밀립니다. osDelay(1000) 은 "지금부터 1000 틱" 이라 printf 에 걸린 시간(약 3 ms)이 쌓이기 때문입니다.

osDelay · osDelayUntil · HAL_Delay#

함수기다리는 동안기준쓰는 곳
osDelay(n)Blocked — 다른 태스크 실행지금부터 n 틱대부분의 대기
osDelayUntil(t)Blocked절대 틱 t 까지정확한 주기 작업 (밀리지 않음)
HAL_Delay(n)바쁜 대기 — 틱을 확인하며 CPU 를 붙잡음지금부터 n ms커널 시작 전 초기화에서만

태스크 안에서 HAL_Delay 를 쓰면 그 태스크가 Running 상태로 CPU 를 붙잡으므로 낮은 우선순위 태스크가 멈춥니다. 커널 시작 뒤에는 osDelay 를 씁니다.

c
uint32_t next = osKernelGetTickCount();
for (;;) {
  next += 1000;
  osDelayUntil(next);          /* 작업 시간과 상관없이 정확히 1000 틱 간격 */
  do_periodic_work();
}

예제 2 — 우선순위와 굶주림#

  • lowTask(Low): osDelay 없이 low_count++ 만 반복 → 다른 태스크가 모두 쉴 때만 돕니다.
  • highTask(AboveNormal): 100 ms 마다 LD2 토글. B1 을 누르고 있는 동안은 양보 없이 바쁜 대기를 합니다(나쁜 예).
  • defaultTask(Normal): osDelayUntil 로 1 초마다 low_count 와 늦어진 시간(late)을 보고합니다.
시뮬레이터에서 열기우선순위 관찰 열기새 창l22-rtos-prio
cCore/Src/main.c
void StartDefaultTask(void *argument)   /* osPriorityNormal */
{
  uint32_t next = osKernelGetTickCount();
  for(;;)
  {
    next += 1000;
    osDelayUntil(next);                 // 절대 시각까지 대기 → 주기가 밀리지 않음
    uint32_t now = osKernelGetTickCount();
    printf("[%5lu] late=%lu ms  low_count=%lu  high_runs=%lu\r\n", now, now - next, low_count, high_runs);
    low_count = 0;
    high_runs = 0;
  }
}

void StartLowTask(void *argument)       /* osPriorityLow — osDelay 없음 */
{
  for(;;)
  {
    low_count++;
  }
}

void StartHighTask(void *argument)      /* osPriorityAboveNormal */
{
  for(;;)
  {
    HAL_GPIO_TogglePin(LD2_GPIO_Port, LD2_Pin);
    high_runs++;
    while (HAL_GPIO_ReadPin(B1_GPIO_Port, B1_Pin) == GPIO_PIN_RESET) { }   // 누르는 동안 양보 없이 바쁜 대기 (나쁜 예)
    osDelay(100);                       // 정상: 100 ms 동안 Blocked → 낮은 태스크에게 CPU
  }
}

시뮬레이터에서 B1 을 약 0.5 초 누르고 있으면 이런 줄이 보입니다.

text
[ 2004] late=0 ms  low_count=1989600  high_runs=10
[ 3423] late=419 ms  low_count=1817201  high_runs=10
[ 4004] late=0 ms  low_count=1149600  high_runs=6
  • 누르는 동안 highTask 가 CPU 를 붙잡아 defaultTask(보통)는 419 ms 늦게 보고하고, lowTask 는 그동안 한 번도 돌지 못해 low_count 가 줄어듭니다.
  • 손을 떼면 곧바로 정상으로 돌아옵니다. lowTask 가 쉬지 않고 돌아도 highTask 의 100 ms 주기는 흔들리지 않습니다 — 선점 덕분입니다.
  • 실물에서는 Idle 태스크보다 높은 태스크가 쉬지 않으면 Idle 이 돌지 못해, 삭제된 태스크의 메모리 정리나 Idle 훅 저전력 진입이 일어나지 않습니다.
시뮬레이터와 HAL_Delay

시뮬레이터는 태스크 안의 HAL_Delay 를 CPU 를 붙잡는 바쁜 대기로 정확히 흉내 내지 못할 수 있습니다. 그래서 예제 2는 바쁜 대기를 while 로 직접 만들었습니다. 실물에서 HAL_Delay 도 같은 결과를 냅니다.

스택 크기#

CubeMX 의 Stack Size 는 워드(4바이트) 단위입니다. 128 워드 = 512 바이트. 태스크의 지역 변수, 함수 호출 깊이, 인터럽트가 끼어들 때 쌓이는 레지스터가 여기에 들어갑니다.

  • printf(newlib)는 스택을 많이 씁니다. printf 를 쓰는 태스크는 256 워드 이상, 실수 출력(%f)까지 쓰면 더 크게 잡습니다.
  • 큰 배열은 지역 변수로 두지 말고 전역(또는 static)으로 둡니다.
  • 실물에서는 osThreadGetStackSpace(handle)(남은 스택의 최솟값)으로 여유를 확인하고, FreeRTOS 설정의 CHECK_FOR_STACK_OVERFLOW 를 켜 두면 넘칠 때 훅이 불립니다(시뮬레이터 미지원).
  • 여러 태스크가 printf 를 쓰면 CubeMX 의 USE_NEWLIB_REENTRANT 를 켜라는 안내가 나옵니다. 켜 두세요.
