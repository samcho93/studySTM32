## 학습 목표

- Cortex-M 이 **RISC · 하버드 구조 · Thumb-2 명령 집합**을 가진 코어라는 것을 각 용어의 뜻과 함께 설명할 수 있습니다.
- 코어 레지스터 R0~R12, SP(MSP/PSP), LR, PC, xPSR 과 특수 레지스터(PRIMASK · BASEPRI · CONTROL)의 역할을 압니다.
- 스레드 모드 · 핸들러 모드, 특권 · 비특권 레벨이 무엇이고 언제 바뀌는지 압니다.
- C 함수 호출이 레지스터와 스택을 어떻게 쓰는지(AAPCS)를 알고, 예외 진입 때 하드웨어가 **8워드를 자동으로 스태킹**하는 이유를 설명할 수 있습니다.
- M0 · M0+ · M3 · M4 · M7 · M33 의 차이(FPU · DSP · MPU · 캐시 · TrustZone)를 표로 구분하고, DMIPS 와 CoreMark 수치를 읽을 수 있습니다.
- CMSIS-Core 의 `__disable_irq()`, `__NOP()`, `NVIC_*` 함수가 어떤 명령·레지스터로 이어지는지 압니다.

## 코어와 MCU 의 경계

STM32 칩 안에서 **Arm 이 설계한 부분은 코어(CPU) · NVIC · SysTick · 디버그 블록**이고, 나머지(GPIO · 타이머 · UART · 플래시 컨트롤러 · 클럭 회로)는 ST 가 설계합니다.
그래서 Cortex-M 에 관한 문서는 Arm 이(*PM0214* 는 ST 가 Arm 문서를 정리한 것), 주변장치 문서는 ST 가(*RM0383*) 씁니다.

| 문서 | 내용 | 누가 씀 |
|---|---|---|
| Armv7-M Architecture Reference Manual | 명령 집합, 예외 모델, 메모리 모델의 규격 | Arm |
| Cortex-M4 Technical Reference Manual | 코어 구현 세부 (파이프라인, 사이클 수) | Arm |
| **PM0214** STM32 Cortex-M4 programming manual | 위 두 문서에서 STM32 개발자에게 필요한 부분 | ST |
| **RM0383** Reference manual | ST 주변장치 레지스터 | ST |
| **DS10314** Datasheet | 전기 특성, 핀 배치, 패키지 | ST |

코어가 같으면 **레지스터 · 명령 · 예외 처리 · 스택 규칙은 모든 제조사의 MCU 에서 같습니다.** NXP, Nordic, Microchip 의 Cortex-M4 도 이 레슨의 내용이 그대로 적용됩니다.

## RISC · 하버드 · Thumb-2

### RISC

Cortex-M 은 **RISC(Reduced Instruction Set Computer)** 입니다. 명령 하나가 하는 일이 단순하고(레지스터끼리 연산, 메모리 로드/스토어 분리), 대부분의 명령이 1 사이클에 끝납니다.
메모리에 있는 값을 계산하려면 반드시 **레지스터로 읽어 와서(LDR) 계산하고 다시 쓰는(STR)** 로드/스토어 구조입니다.

```text
GPIOA->ODR ^= (1 << 5);        // C 한 줄은
  ldr  r3, [r2, #20]           // 1. ODR 을 r3 으로 읽고     (r2 = GPIOA 베이스, 0x14 = ODR 오프셋)
  eor  r3, r3, #32             // 2. 비트 5 를 반전하고
  str  r3, [r2, #20]           // 3. 다시 씀  → 읽기·수정·쓰기 (RMW) 세 명령
```

이 세 명령 사이에 인터럽트가 끼어들 수 있다는 점이 [T05](t05.html) 의 BSRR 이야기로 이어집니다.

### 하버드 구조

**명령 버스(I-bus)와 데이터 버스(D-bus)가 분리**되어 있어 명령 페치와 데이터 접근이 동시에 일어납니다.
Cortex-M3/M4 는 세 개의 AHB-Lite 버스를 가집니다.

| 버스 | 주소 범위 | 용도 |
|---|---|---|
| I-Code | 0x0000_0000 ~ 0x1FFF_FFFF | 명령 페치 (플래시) |
| D-Code | 0x0000_0000 ~ 0x1FFF_FFFF | 코드 영역의 데이터 읽기 (상수 테이블, 리터럴 풀) |
| System | 0x2000_0000 ~ 0xDFFF_FFFF | SRAM, 주변장치, 외부 메모리 |

주소 공간은 하나(폰 노이만처럼 통합)지만 버스가 나뉘어 있어 "수정된 하버드" 라고 부릅니다.
SRAM 에 놓인 코드를 실행하면 System 버스로 명령을 가져오므로 조금 느려질 수 있습니다. Cortex-M0/M0+ 는 버스가 하나(폰 노이만)입니다.

### Thumb-2

Arm 코어는 원래 32비트 고정 길이 명령(A32)을 썼습니다. Thumb 은 자주 쓰는 명령을 16비트로 줄인 것이고, **Thumb-2** 는 16비트와 32비트 명령을 섞어 쓰는 집합입니다.
Cortex-M 은 **Thumb-2 만** 실행합니다. 그래서 다음 두 가지가 따라옵니다.

- 코드 밀도가 높습니다. 같은 프로그램이 A32 보다 25~30 % 작습니다 (Arm 발표 수치 기준).
- 모든 코드 주소의 **최하위 비트(bit 0)가 1** 이어야 합니다. 이 비트는 "Thumb 상태" 표시(xPSR 의 T 비트로 들어감)이며, 벡터 테이블에 있는 핸들러 주소가 모두 홀수인 이유입니다. 함수 포인터에 짝수 주소를 넣고 호출하면 **HardFault** 가 납니다.

Cortex-M0/M0+ 는 Thumb-2 의 부분집합(대부분 16비트 명령, 32비트는 BL·MSR·MRS·DMB·DSB·ISB 정도)만 지원합니다. 그래서 M0 용 코드는 M4 에서 돌지만 반대는 안 됩니다.

## 코어 레지스터

@table[regmap]
| 레지스터 | 이름 | 역할 |
|---|---|---|
| R0 ~ R3 | 인자 · 반환 | 함수 인자 4개까지, 반환값 (R0, 64비트면 R0:R1). 호출자가 보존 (caller-saved) |
| R4 ~ R11 | 변수 | 함수가 쓰면 스스로 저장·복원 (callee-saved) |
| R12 | IP | 링커 · 호출 중간 임시. caller-saved |
| R13 | **SP** | 스택 포인터. MSP 와 PSP 두 개 중 하나가 보임 |
| R14 | **LR** | 링크 레지스터. `bl` 로 함수 호출 시 복귀 주소. 예외 안에서는 EXC_RETURN 코드 |
| R15 | **PC** | 프로그램 카운터. 읽으면 현재 명령 + 4 |
| xPSR | 상태 | APSR(N Z C V Q 플래그) + IPSR(현재 예외 번호) + EPSR(T 비트, IT/ICI 상태) |
| PRIMASK | 마스크 | 1 이면 NMI · HardFault 외 모든 예외 차단 (`cpsid i`) |
| FAULTMASK | 마스크 | 1 이면 NMI 외 모두 차단 (M0/M0+ 없음) |
| BASEPRI | 마스크 | 이 값 이상의(숫자가 크거나 같은) 우선순위 예외 차단. 0 이면 무효 (M0/M0+ 없음) |
| CONTROL | 제어 | bit0 nPRIV (스레드 모드 비특권), bit1 SPSEL (PSP 사용), bit2 FPCA (FPU 사용 중) |

범용 레지스터가 13개뿐이라 컴파일러는 지역 변수를 최대한 레지스터에 두고, 모자라면 스택에 내립니다. 최적화 옵션(`-O0` vs `-O2`)에 따라 같은 코드의 스택 사용량이 크게 다른 이유입니다.

### 두 개의 스택 포인터

SP 는 물리적으로 **MSP(Main SP)** 와 **PSP(Process SP)** 두 개입니다.

- 리셋 직후와 모든 **예외 핸들러**는 MSP 를 씁니다.
- 스레드 모드에서 CONTROL.SPSEL = 1 이면 PSP 를 씁니다. RTOS 가 각 태스크에 PSP 를 따로 주고, 커널과 인터럽트는 MSP 를 쓰도록 나눕니다.
- HAL 만 쓰는 이 강좌의 코드는 처음부터 끝까지 MSP 하나만 씁니다. 링커 스크립트의 `_estack` (F411: 0x2002_0000 = SRAM 끝) 이 그 초기값입니다.

## 동작 모드와 특권 레벨

| | 스레드 모드 (Thread) | 핸들러 모드 (Handler) |
|---|---|---|
| 언제 | `main()` 을 포함한 보통 코드 | 예외·인터럽트 핸들러 실행 중 |
| 특권 | 특권 또는 비특권 (CONTROL.nPRIV) | 항상 특권 |
| SP | MSP 또는 PSP | 항상 MSP |
| IPSR | 0 | 예외 번호 (SysTick = 15, EXTI0 = 22 …) |

리셋하면 **스레드 모드 · 특권**으로 시작합니다. HAL 프로젝트는 계속 특권 상태로 돌기 때문에 모든 레지스터에 접근할 수 있고, `cpsid i` 로 인터럽트를 끌 수도 있습니다.
비특권으로 내려가면(CONTROL.nPRIV = 1) 시스템 레지스터 접근과 `cpsid` 가 금지되고, MPU 로 막은 영역을 건드리면 MemManage 폴트가 납니다.
비특권에서 특권으로 올라가는 유일한 길은 **SVC 명령으로 예외를 일으키는 것**이며, RTOS 의 시스템 콜이 이 구조를 씁니다.

`HAL_GPIO_EXTI_Callback` 처럼 인터럽트에서 불리는 함수 안에서 `__get_IPSR()` 을 읽으면 0 이 아닌 값이 나옵니다. "지금 ISR 안인가?" 를 판단하는 표준 방법입니다.

## 함수 호출과 스택 (AAPCS)

Arm 의 호출 규약 **AAPCS(Procedure Call Standard for the Arm Architecture)** 는 컴파일러가 지켜야 하는 약속입니다.

1. 인자는 **R0, R1, R2, R3** 순서로 넘기고, 5번째부터는 스택에 쌓습니다. 64비트 인자(`uint64_t`, `double`)는 짝수 레지스터 쌍(R0:R1, R2:R3)을 씁니다.
2. 반환값은 **R0** (64비트는 R0:R1) 입니다. 구조체가 크면 호출자가 공간을 마련해 주소를 R0 로 넘깁니다.
3. **R0~R3, R12 는 호출된 함수가 마음대로 써도 됩니다** (caller-saved). 값을 지키고 싶으면 호출자가 미리 저장합니다.
4. **R4~R11 은 호출된 함수가 쓰려면 반드시 저장하고 복원**해야 합니다 (callee-saved). 함수 첫머리의 `push {r4, r5, lr}` 가 그것입니다.
5. 스택은 **아래로 자라며(full-descending)**, 함수 경계에서 **8바이트 정렬**을 유지합니다.

```c
uint32_t add3(uint32_t a, uint32_t b, uint32_t c) { return a + b + c; }
/*   add  r0, r0, r1      ; a + b          — r0 = a, r1 = b, r2 = c 로 들어옴
     add  r0, r0, r2      ; + c            — 결과를 r0 에
     bx   lr              ; 복귀 (lr 에 호출 다음 주소)                                   */
```

인자가 넷 이하이고 지역 변수가 적으면 함수가 스택을 전혀 쓰지 않을 수 있습니다. `bl` 명령이 복귀 주소를 LR 에 넣고, 다른 함수를 또 부르려면 그 LR 을 스택에 `push` 해야 합니다.

:::info 왜 하드웨어가 딱 8워드를 스태킹하는가
AAPCS 에 따르면 어떤 C 함수를 부르든 **R0~R3, R12, LR 은 깨질 수 있고 R4~R11 은 그 함수가 알아서 지킵니다.**
그래서 예외가 났을 때 코어는 caller-saved 인 R0~R3 · R12 · LR 과, 복귀에 필요한 PC · xPSR — 합쳐서 8워드 — 만 스택에 넣어 두면
**핸들러를 보통의 C 함수로 쓸 수 있습니다.** 핸들러가 R4~R11 을 쓰면 컴파일러가 스스로 push/pop 하기 때문입니다.
이 설계 덕분에 Cortex-M 은 어셈블리 래퍼 없이 `void EXTI0_IRQHandler(void)` 를 그대로 벡터 테이블에 넣을 수 있습니다.
:::

## 파이프라인과 실행 시간

Cortex-M3/M4 는 **3단 파이프라인(페치 → 디코드 → 실행)** 입니다. 명령 대부분이 1 사이클이지만 다음은 예외입니다.

| 명령 | 사이클 (M3/M4) | 비고 |
|---|---|---|
| 산술 · 논리 · 시프트 | 1 | |
| 32 × 32 곱셈 `mul` | 1 | M0 은 1 또는 32 (구현 선택) |
| 나눗셈 `udiv` `sdiv` | 2 ~ 12 | 값에 따라 다름. M0/M0+ 는 하드웨어 나눗셈 없음 (라이브러리 호출, 수십 사이클) |
| 로드 `ldr` | 2 (연속이면 파이프라이닝) | 플래시 대기 상태가 더해질 수 있음 |
| 분기 (taken) | 2 ~ 4 | 파이프라인 비움. M3/M4 는 분기 예측 없음, M7 은 있음 |
| `bl` 함수 호출 | 2 ~ 4 | |

플래시가 코어보다 느리기 때문에(F411 84 MHz 에서 2 대기 상태, [T04](t04.html)) ST 는 F4 에 **ART Accelerator**(명령 프리페치 + 64 × 128비트 캐시)를 넣어 0 대기 상태처럼 보이게 합니다.
Cortex-M7 은 6단 슈퍼스칼라(1 사이클에 2 명령) 파이프라인과 진짜 L1 캐시(명령·데이터)를 가집니다. M0+ 는 2단 파이프라인이라 분기 손실이 작습니다.

`HAL_Delay(1)` 이 84 MHz 에서 84,000 사이클이라는 것, `for` 루프 한 바퀴가 대략 3~5 사이클이라는 것을 감으로 알아 두면 "이 코드가 1 ms 안에 끝나는가" 를 어림할 수 있습니다.

## 예외 진입과 복귀

@fig[exception-entry] 왼쪽은 F411 벡터 테이블의 일부, 오른쪽은 예외 진입 때 하드웨어가 쌓는 8워드와 진입 순서입니다.

예외(exception)는 인터럽트를 포함하는 넓은 말입니다. Cortex-M 에서는 리셋 · NMI · HardFault · SVC · PendSV · SysTick 같은 **시스템 예외 1~15번**과 주변장치 **인터럽트(IRQ) 16번부터**가 하나의 벡터 테이블에 놓입니다.

| 예외 번호 | 이름 | 우선순위 | 원인 |
|---|---|---|---|
| 1 | Reset | −3 (고정) | 리셋 |
| 2 | NMI | −2 (고정) | 클럭 보안(CSS) 등, 마스크 불가 |
| 3 | HardFault | −1 (고정) | 다른 폴트가 처리되지 못했을 때, 벡터 오류 |
| 4 | MemManage | 설정 | MPU 위반, 실행 불가 영역 실행 |
| 5 | BusFault | 설정 | 잘못된 주소 접근 (예: 클럭 안 켠 주변장치) |
| 6 | UsageFault | 설정 | 정의되지 않은 명령, 0 나눗셈(옵션), 정렬 오류 |
| 11 | SVCall | 설정 | `svc` 명령 (RTOS 시스템 콜) |
| 12 | DebugMonitor | 설정 | 디버그 이벤트 |
| 14 | PendSV | 설정 | 소프트웨어로 pending (RTOS 문맥 전환) |
| 15 | SysTick | 설정 | SysTick 타이머 (HAL 의 1 ms 틱) |
| 16 ~ | IRQ0 ~ | 설정 | 주변장치 (F411: WWDG = IRQ0 … SPI5 = IRQ85) |

진입 과정은 그림의 1~5 단계입니다. 핵심은 **하드웨어가 스태킹 · 벡터 페치 · 복귀를 모두 처리**하므로 핸들러가 보통의 C 함수라는 것입니다.
진입 지연은 M3/M4 에서 **12 사이클**(0 대기 상태 메모리 기준), M0 16, M0+ 15, M7 12 사이클입니다. 84 MHz 에서 12 사이클은 약 143 ns 입니다.

복귀는 핸들러가 `bx lr` 를 실행할 때 LR 에 든 **EXC_RETURN** 값을 보고 일어납니다.

| EXC_RETURN | 뜻 |
|---|---|
| 0xFFFF_FFF1 | 핸들러 모드로 복귀, MSP (중첩 인터럽트에서 복귀) |
| 0xFFFF_FFF9 | 스레드 모드로 복귀, MSP (HAL 프로젝트의 보통 경우) |
| 0xFFFF_FFFD | 스레드 모드로 복귀, PSP (RTOS 태스크로 복귀) |
| 0xFFFF_FFE1 / E9 / ED | 위와 같되 FPU 문맥이 스택에 있음 (M4F, M7) |

디버거에서 폴트가 나 멈췄을 때 LR 이 `0xFFFFFFF9` 이면 "메인 코드 실행 중 예외 진입" 이라는 뜻이고, 스택의 여섯 번째 워드(PC)를 보면 폴트가 난 명령 주소를 알 수 있습니다.

:::tip 예외 중첩과 우선순위
높은 우선순위(숫자가 작은) 예외는 실행 중인 낮은 우선순위 핸들러를 **다시 8워드 스태킹하고** 끼어듭니다. 이때 LR = 0xFFFF_FFF1 입니다.
한 핸들러가 끝날 때 대기 중인 다른 예외가 있으면 pop → push 를 생략하고 바로 다음 핸들러로 가는 **테일체이닝(tail-chaining, 6 사이클)** 이 일어납니다. [T06](t06.html) 에서 NVIC 우선순위와 함께 다룹니다.
:::

- **FPU** 가 없으면 `float` 연산이 소프트웨어 라이브러리로 처리되어 수십~수백 사이클이 걸립니다. M4F 의 FPU 는 `float` 만 1 사이클급이고 `double` 은 여전히 소프트웨어입니다. `3.0 * x` 처럼 상수에 `f` 를 빼먹으면 `double` 연산이 되므로 `3.0f * x` 로 씁니다.
- **DSP 명령** 은 16비트 두 쌍을 한 번에 곱해 더하는 SIMD(`SMLAD`), 포화 연산(`SSAT`) 등입니다. CMSIS-DSP 라이브러리(FFT, 필터)가 이것을 씁니다.
- **MPU** 는 메모리 영역별 접근 권한을 정합니다. RTOS 에서 태스크가 남의 스택을 건드리는 것을 막거나, 널 포인터 접근을 폴트로 잡는 데 씁니다.
- **TrustZone(M33)** 은 보안 세계와 비보안 세계를 하드웨어로 나눕니다. 키 저장과 보안 부트가 비보안 코드에서 격리됩니다.

### DMIPS 와 CoreMark

- **DMIPS**(Dhrystone MIPS)는 1980년대 벤치마크 Dhrystone 기준의 정수 성능입니다. 컴파일러 최적화에 민감하고 실제 코드와 다르지만, 제조사가 오래 써 온 지표입니다. F411 은 DS10314 에서 **125 DMIPS (1.25 DMIPS/MHz × 100 MHz)**, H743 은 480 MHz 에서 1027 DMIPS 로 표기됩니다.
- **CoreMark** 는 EEMBC 가 만든 더 현대적인 지표로 리스트 처리 · 행렬 · 상태 기계 · CRC 를 섞어 잽니다. 코어 등급 비교에는 CoreMark/MHz 가 더 공정합니다.
- 두 값 모두 **코어 만의** 수치입니다. 실제 성능은 플래시 대기 상태, 캐시, 버스 경합에 따라 달라지므로 "84 MHz F411 이 72 MHz F103 보다 1.17배 빠르다" 처럼 단순 비교하면 안 됩니다.

## CMSIS-Core

**CMSIS(Cortex Microcontroller Software Interface Standard)** 는 Arm 이 정한 공통 헤더입니다. STM32 프로젝트의 `Drivers/CMSIS/` 아래에 있고, HAL 이 그 위에 얹힙니다.

| 함수 · 매크로 | 실제 동작 | 쓰임 |
|---|---|---|
| `__disable_irq()` / `__enable_irq()` | `cpsid i` / `cpsie i` (PRIMASK = 1 / 0) | 짧은 임계 구역 |
| `__get_PRIMASK()` / `__set_PRIMASK(x)` | `mrs` / `msr` | 임계 구역 진입 전 상태 저장 · 복원 |
| `__set_BASEPRI(x)` | BASEPRI 레지스터 | 특정 우선순위 이상만 차단 (FreeRTOS 가 사용) |
| `__NOP()` | `nop` | 1 사이클 지연, 디버그 중단점 자리 |
| `__WFI()` / `__WFE()` | `wfi` / `wfe` | Sleep 모드 진입 (인터럽트 · 이벤트까지 정지) |
| `__DSB()` `__ISB()` `__DMB()` | 배리어 | 레지스터 쓰기 순서 보장 (VTOR 변경, 캐시 조작 후) |
| `__REV(x)` `__RBIT(x)` `__CLZ(x)` | `rev` `rbit` `clz` | 바이트 순서 뒤집기, 비트 뒤집기, 선행 0 개수 |
| `__LDREXW` / `__STREXW` | `ldrex` / `strex` | 원자적 읽기-수정-쓰기 (M3 이상) |
| `NVIC_EnableIRQ(IRQn)` | NVIC->ISER | HAL 의 `HAL_NVIC_EnableIRQ` 가 이것을 부름 |
| `NVIC_SetPriority(IRQn, p)` | NVIC->IP 또는 SCB->SHP | `HAL_NVIC_SetPriority` 가 그룹 인코딩 후 부름 |
| `NVIC_SetPriorityGrouping(g)` | SCB->AIRCR PRIGROUP | `HAL_Init` 이 그룹 4 로 설정 |
| `NVIC_SystemReset()` | AIRCR.SYSRESETREQ | 소프트웨어 리셋 |
| `SysTick_Config(ticks)` | SysTick LOAD · VAL · CTRL | `HAL_InitTick` 이 사용 |

임계 구역의 올바른 형태는 다음과 같습니다. 이미 인터럽트가 꺼진 상태에서 불릴 수 있으므로 무조건 `__enable_irq()` 로 켜면 안 됩니다.

```c
uint32_t prim = __get_PRIMASK();   // 현재 상태 저장
__disable_irq();
shared_counter++;                   // ISR 과 공유하는 변수 수정 (RMW 세 명령을 보호)
__set_PRIMASK(prim);                // 원래 상태로 (켜져 있었을 때만 켜짐)
```

:::warn 시뮬레이터에서
이 강좌의 시뮬레이터는 HAL 함수 수준을 에뮬레이션하므로 `__disable_irq()` 같은 CMSIS 내장 함수와 인라인 어셈블리는 지원하지 않습니다. 실물 CubeIDE 프로젝트에서 시험해 보세요.
:::

## 리셋 직후에 일어나는 일

1. 코어가 주소 **0x0000_0000** 에서 초기 MSP 값을, **0x0000_0004** 에서 `Reset_Handler` 주소를 읽습니다. 이 주소에는 BOOT 핀 설정에 따라 플래시(0x0800_0000)가 비쳐 있습니다 ([T03](t03.html)).
2. `Reset_Handler`(`startup_stm32f411xetx.s`)가 `SystemInit()` 을 불러 FPU 접근을 켜고(CPACR), VTOR 를 설정합니다.
3. 플래시에 있는 `.data` 초기값을 SRAM 으로 복사하고, `.bss` 를 0 으로 채웁니다.
4. `__libc_init_array()` 로 C++ 생성자 · 라이브러리 초기화를 하고 `main()` 을 부릅니다.
5. `main()` 이 `HAL_Init()` 을 부르면 NVIC 그룹, SysTick 1 ms, 플래시 프리페치 · 캐시가 설정되고, `SystemClock_Config()` 가 PLL 을 켭니다 ([T04](t04.html)).

이 순서를 알면 "전역 변수 초기값이 왜 자동으로 들어가는가", "`main()` 전에 클럭이 왜 16 MHz 인가" 같은 질문에 답할 수 있습니다.

:::check 스스로 확인
- 함수 인자가 6개면 5 · 6번째는 어디로 전달됩니까?
- ISR 안에서 R4 를 쓰면 누가 저장 · 복원합니까? R0 는?
- `float` 를 쓰는 코드를 F103 으로 옮기면 실행 시간이 왜 크게 늘어납니까?
- LR 이 0xFFFF_FFFD 로 끝나는 복귀는 어떤 상황입니까?
:::

## 자주 나는 오류와 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| 실행 직후 `HardFault_Handler` 의 `while(1)` 에 멈춤 | 널 포인터, 클럭을 켜지 않은 주변장치 접근(BusFault 승격), 스택 오버플로, 짝수 주소 함수 포인터 | 디버거에서 SCB->CFSR · HFSR 과 스택의 PC 워드 확인. 주변장치 클럭 인에이블 순서 점검 |
| `float` 연산이 예상보다 훨씬 느림 | FPU 미사용 (`-mfloat-abi=soft`), `double` 로 계산됨 | 프로젝트 설정 FPU = fpv4-sp-d16, `hard` ABI, 상수에 `f` 접미사 |
| 인터럽트를 끈 뒤 시스템이 멈춤 | `__disable_irq()` 후 `HAL_Delay` (SysTick 차단) | 임계 구역에서 HAL_Delay 금지, PRIMASK 저장 · 복원 패턴 사용 |
| 최적화를 켜니 동작이 달라짐 | ISR 과 공유하는 변수에 `volatile` 없음 (레지스터에 캐시됨) | `volatile` 선언, 임계 구역 |
| 링크 오류 `undefined reference to __aeabi_uidiv` (M0) | M0 에는 나눗셈 명령이 없어 라이브러리 필요 | 표준 라이브러리 링크 확인 (CubeIDE 는 자동) |
| 스택 오버플로로 전역 변수가 깨짐 | 큰 지역 배열, 깊은 재귀 | 링커 `_Min_Stack_Size` 늘리기, 큰 버퍼는 `static` 으로 |

## 과제

1. `uint32_t f(uint32_t a, uint32_t b, uint32_t c, uint32_t d, uint32_t e)` 를 호출할 때 각 인자가 어디에 놓이는지, 반환값은 어디에 오는지 적으세요.
2. 예외 진입 때 스택에 쌓이는 8워드를 낮은 주소부터 순서대로 쓰고, 왜 R4~R11 은 쌓지 않는지 AAPCS 로 설명하세요.
3. CubeIDE 프로젝트의 `startup_stm32f411xetx.s` 를 열어 `Reset_Handler` 가 하는 일을 순서대로 적고, `.data` 복사 루프를 찾으세요.
4. F411 (M4F, 100 MHz) 과 F103 (M3, 72 MHz) 의 DMIPS 를 계산하고, `float` 를 많이 쓰는 코드에서 두 칩의 실제 성능 차이가 DMIPS 비율보다 큰 이유를 쓰세요.
5. (실물) 디버거로 `HAL_GPIO_EXTI_Callback` 안에 중단점을 걸고 레지스터 창의 LR · xPSR(IPSR) · SP 값을 기록한 뒤, 이 레슨의 표와 대조하세요.
